01 · Le problème

Une souscription habitation s'appuie sur 3 contrats d'API.
Le parcours qui les enchaîne, lui, n'est décrit nulle part.

Dans quel ordre appeler ? Quelle donnée passe d'un appel au suivant ? Que faire si un appel échoue ? Aujourd'hui : un wiki, un diagramme de séquence qui vieillit, ou la tête d'un architecte.

Vocabulaire : ici « contrat » = contrat d'API (OpenAPI/AsyncAPI), pas contrat d'assurance. L'exemple parle donc de « police émise ». Question à la salle : qui a déjà eu une recette cassée alors que chaque API respectait son contrat ?

02 · Définition

Arazzo, c'est quoi ?

Une norme de l'OpenAPI Initiative (Linux Foundation) pour décrire, en YAML ou JSON, une suite d'appels d'API : leur ordre, les données qui passent de l'un à l'autre, et ce qui fait qu'une étape est réussie.

arazzo « tapisserie » en italien — on tisse des API existantes en un parcours.

Lisible

Un format structuré (YAML ou JSON), relu en PR comme du code.

Déterministe

Même entrée, mêmes étapes, mêmes critères. Pas d'interprétation.

Spécifié

Chaque étape déclare son critère de succès : « réussi » est écrit, pas supposé.

Définition à retenir : Arazzo décrit une suite d'appels d'API, leur ordre, les données échangées et les critères de succès. Arazzo = tapisserie en italien : il tisse des API qui existent déjà.
02 · Définition

Ce qu'Arazzo est — et ce qu'il n'est pas

C'est

  • Un contrat : la description de référence d'un parcours.
  • Une couche au-dessus d'OpenAPI et d'AsyncAPI, qu'il référence.
  • Un fichier versionné dans git, revu en PR.
  • Une spécification : ordre, données échangées, critères de succès, reprises.

Ce n'est pas

  • Un orchestrateur : il ne tourne pas en production (ni BPMN, ni Temporal, ni saga).
  • Un remplaçant d'OpenAPI / AsyncAPI : sans eux, il n'a rien à référencer.
  • Un programme : il spécifie, il n'exécute rien.
  • Un diagramme : c'est une spécification structurée, versionnée et relue.
Le malentendu le plus fréquent : « c'est un moteur de workflow ». Non. Arazzo décrit ; il ne remplace pas notre code d'orchestration.
03 · État des lieux — octobre 2026

Trois normes, trois questions

NormeRépond àVersionCe qui compte pour nous
OpenAPIQue fait cet appel HTTP ?3.2.0 sept. 2025QUERY, streaming (text/event-stream, jsonl), tags hiérarchiques. Sans rupture vs 3.1.
AsyncAPIQuel message circule sur ce canal ?3.1.0 janv. 2026La 3.0 a séparé canaux et opérations send/receive. La 3.1 est mineure.

OpenAPI décrit une opération. AsyncAPI décrit un message. Arazzo décrit l'enchaînement. Point clé pour nous : Arazzo 1.0 ne parlait que REST ; la 1.1 (mai 2026) gère aussi Kafka.

Les expressions : le fil qui relie les étapes

ExpressionLit…Exemple

$statusCodele code HTTP de la réponse$statusCode == 201
$response.body#/…un champ de la réponse (JSON Pointer)$response.body#/id
$steps.s.outputs.yune sortie d'une étape précédente$steps.creerDevis.outputs.quoteId
$workflows.w.outputs.yune sortie d'un autre workflow$workflows.identifierClient.outputs.customerId
$sourceDescriptions.n.opune opération d'un contrat d'API$sourceDescriptions.quoteApi.createQuote

À retenir : $steps.…outputs rend explicite ce qu'on se transmet entre équipes.

Les expressions rendent la spécification précise : on sait exactement d'où vient chaque valeur.
05 · Un exemple complet

Du devis à la police, en un workflow

3 étapes au clavier : nominal → retry → ordre non respecté. Nominal : le parcours démarre après le workflow identifierClient (dependsOn de workflow), puis chaque étape lit les outputs de la précédente. Retry : la reprise est DANS le contrat, pas dans un runbook. Ordre non respecté : on ne paie jamais avant l'éligibilité. Le dependsOn rend cette règle contractuelle : le parcours la spécifie noir sur blanc.
05 · Un exemple complet

Le fichier : sources et premières étapes

souscription-habitation.arazzo.yamlArazzo 1.1.0
arazzo: 1.1.0
sourceDescriptions:                                       # les contrats d'API, référencés
  - { name: quoteApi,   type: openapi, url: ./quote-api.openapi.yaml }
  - { name: paymentApi, type: openapi, url: ./payment-api.openapi.yaml }
  - { name: policyApi,  type: openapi, url: ./policy-api.openapi.yaml }
workflows:
  - workflowId: identifierClient                            # étapes non détaillées ici
  - workflowId: souscrireHabitation
    dependsOn: [ identifierClient ]                         # un parcours prérequis
    steps:
      - stepId: creerDevis
        operationId: $sourceDescriptions.quoteApi.createQuote
        requestBody:
          payload: { customerId: $workflows.identifierClient.outputs.customerId }
        successCriteria: [ { condition: $statusCode == 201 } ]
        outputs: { quoteId: $response.body#/id }
      - stepId: verifierEligibilite
        operationId: $sourceDescriptions.quoteApi.checkEligibility
        parameters: [ { name: id, in: path, value: $steps.creerDevis.outputs.quoteId } ]
        successCriteria: [ { condition: $response.body#/eligible == true } ]
clé structure Arazzo$… expression# … commentaire
dependsOn de workflow : souscrireHabitation ne démarre qu'une fois identifierClient terminé, et réutilise sa sortie via $workflows.identifierClient.outputs.customerId. On compose des parcours comme des briques.
05 · Un exemple complet

dependsOn : un prérequis écrit dans le contrat

… suite du workflowdependsOn d'étape
- stepId: payer
  operationId: $sourceDescriptions.paymentApi.pay
  # prérequis explicite. Selon la spec Arazzo,
  # en synchrone l'ordre de steps suffit : dependsOn
  # sert surtout à l'asynchrone (voir annexe).
  dependsOn: [ verifierEligibilite ]   # jamais avant
  requestBody:
    payload: { quoteId: $steps.creerDevis.outputs.quoteId }
  successCriteria: [ { condition: $statusCode == 201 } ]
  onFailure:
    - { name: indispo, type: retry,
        retryAfter: 2, retryLimit: 3,
        criteria: [ { condition: $statusCode == 503 } ] }
  outputs: { paymentId: $response.body#/id }
- stepId: emettrePolice
  operationId: $sourceDescriptions.policyApi.issuePolicy
  successCriteria: [ { condition: $statusCode == 201 } ]
  outputs: { policyId: $response.body#/policyId }

Entre workflows

Composer des parcours : souscrireHabitation après identifierClient.

Entre étapes

Une règle métier devient contractuelle : on ne paie pas avant l'éligibilité. Réordonner le fichier ne peut plus la casser en silence.

Nuance de la spec

En synchrone, l'ordre du tableau steps suffit. dependsOn sert surtout à l'asynchrone et à expliciter un prérequis.

dependsOn d'étape : « liste des étapes qui DOIVENT être terminées avant celle-ci ». Il n'exécute rien : il pose un prérequis. Être honnête : la spec recommande l'ordre du tableau pour le synchrone ; dependsOn est surtout pensé pour l'asynchrone. Son intérêt ici : rendre la règle métier explicite dans le contrat. L'étape événementielle (AsyncAPI) est en annexe si la question vient.
06 · Esprit critique

Pourquoi y aller — et ce qui peut coincer

Ce qu'on gagne

  • Une source de vérité du parcours, revue en PR avec les contrats d'API.
  • Spécifié : ordre, données et critères de succès écrits noir sur blanc.
  • Norme ouverte (OpenAPI Initiative) : pas de verrou éditeur.
  • Partagé : archis, devs et QA lisent le même fichier.
  • REST + Kafka dans un même parcours depuis la 1.1.

Ce qui peut coincer

  • Norme jeune : la 1.1 date de mai 2026, peu de retours d'expérience.
  • Prérequis : sans contrats d'API à jour, l'Arazzo ment.
  • Maintenance : un fichier de plus. Qui en est propriétaire ?
  • Hors norme : les jeux de données ne sont pas couverts par la spec.
Mon parti pris : commencer par un parcours critique, multi-équipes, qui casse en recette. Si en 3 mois il n'a pas clarifié le parcours entre les équipes, on arrête.
Être honnête sur les limites : c'est ce qui rend crédible. Critère de succès explicite pour l'expérimentation : un parcours mieux compris entre équipes en 3 mois.

07 · Ce que montre le prototype

Microcks vérifierait les appels reçus

Ce qu'on voit

  • L'application a appelé les mocks Microcks.
  • Microcks compare ces appels au workflow Arazzo.
  • Verdict : échec, le paiement a été appelé avant la réservation de stock — exactement un prérequis de type dependsOn.
  • L'étape fautive, la requête et la réponse sont affichées.

Pour le QA et le dev

Un verdict qui pointe l'étape, pas un log de 3 000 lignes.

C'est le « check » de l'hypothèse : vérifier qu'une application respecte l'ordre décrit dans le contrat Arazzo. Question : est-ce que ce verdict vous aurait fait gagner du temps sur votre dernier incident de recette ?

08 · Si l'hypothèse tient

Un fichier, trois métiers

Architecte

Aujourd'huiséquences dans un wiki, vite obsolètes.

Demainécrit le workflow, le revoit en PR avec les contrats d'API.

Développeur

Aujourd'huiattend l'équipe voisine, ou bricole des bouchons.

Demaincode contre les mocks du parcours, sait quels outputs les autres attendent.

Testeur / QA

Aujourd'huiscénarios bout-en-bout manuels, hors contrat.

Demainvérifie le workflow en CI, lit l'étape et le critère en échec.

Le fichier vit dans git, à côté des contrats d'API. La boucle : l'archi décrit, le dev code contre les mocks, le QA vérifie en CI, les régressions reviennent à l'archi. Architectes : contribuer à l'écriture des workflows. QA : utiliser ces workflows pour vérifier nos applications.

Annexe · nouveau en Arazzo 1.1

L'étape événementielle

policy-events : attendre la police émiseAsyncAPI step
- stepId: attendrePoliceEmise
  operationId: $sourceDescriptions.policyEvents.onPolicyIssued
  action: receive
  dependsOn: [ payer ]
  correlationId: $steps.payer.outputs.paymentId
  timeout: 30000                  # ms
  successCriteria:
    - context: $message.payload
      condition: $.status == 'ISSUED'
      type: jsonpath
  outputs:
    policyId: $message.payload.policyId

action

send publie un message, receive en attend un, sur un canal du contrat AsyncAPI (type: asyncapi).

correlationId

Relie le message reçu à ce parcours. Doit être aligné avec celui déclaré dans le contrat AsyncAPI.

timeout · $message

Délai max d'attente en ms ; $message.payload lit le message reçu. Ici, dependsOn prend tout son sens.

Annexe, à montrer si la question Kafka vient. C'est le cas d'usage principal de dependsOn d'étape selon la spec : coordonner l'asynchrone.
