Le constat

Dans quel ordre appeler ? Quelle donnée passe d'un appel au suivant ? Que faire si un appel échoue ? Aujourd'hui : un wiki, un diagramme de séquence qui vieillit, ou la tête d'un architecte.

01 · Le problème

Un contrat par API, aucun pour le parcours

Aujourd'hui : chaque API a son contrat d'API. Les « ? » sont là où les recettes cassent.

Avec Arazzo : les contrats d'API ne changent pas, on ajoute le contrat du parcours au-dessus.

⏱ 4:30 — Clic : bascule « Avec Arazzo ». On ne touche pas aux contrats d'API existants : on ajoute un contrat de plus, celui DU parcours.

02 · Définition

Arazzo, c’est quoi ?

Une norme de l’OpenAPI Initiative (Linux Foundation) pour décrire, en YAML ou JSON, une suite d’appels d’API : leur ordre, les données qui passent de l’un à l’autre, et ce qui fait qu’une étape est réussie.

arazzo signifie « tapisserie » en italien : on tisse des API existantes en un parcours.

Lisible

Un format structuré, relu en PR comme du code.

Déterministe

Même entrée, mêmes étapes, mêmes critères.

Spécifié

« Réussi » est écrit, pas supposé.

⏱ 7:00 — Définition à retenir : Arazzo spécifie une suite d'appels d'API, leur ordre, les données échangées et les critères de succès. Arazzo = tapisserie : il tisse des API qui existent déjà.

02 · Définition

Ce qu’Arazzo est, et ce qu’il n’est pas

C'est

  • Un contrat : la description de référence d'un parcours
  • Une couche au-dessus d'OpenAPI et d'AsyncAPI
  • Un fichier versionné dans git, revu en PR
  • Une spécification : ordre, données, critères, reprises

Ce n'est pas

  • Un orchestrateur : ni BPMN, ni Temporal, ni saga
  • Un remplaçant d'OpenAPI ou d'AsyncAPI
  • Un programme : il spécifie, il n'exécute rien
  • Un diagramme : c'est une spécification structurée

⏱ 9:30 — Le malentendu le plus fréquent : « c'est un moteur de workflow ». Non. Arazzo spécifie ; il ne remplace pas notre code d'orchestration.

03 · État des lieux, octobre 2026

Trois normes, trois questions

Norme Répond à Version
OpenAPI Que fait cet appel HTTP ? 3.2.0 · sept. 2025
AsyncAPI Quel message circule sur ce canal ? 3.1.0 · janv. 2026
Arazzo Dans quel ordre, avec quelles données, et quand est-ce réussi ? 1.1.0 · mai 2026

OpenAPI 3.2 : QUERY, streaming, tags hiérarchiques. AsyncAPI 3.1 : mineure. Arazzo 1.1 ajoute les étapes AsyncAPI : REST et événements dans un même parcours.

⏱ 12:00 — OpenAPI décrit une opération. AsyncAPI décrit un message. Arazzo décrit l'enchaînement. Arazzo 1.0 ne parlait que REST ; la 1.1 gère aussi Kafka.

Corollaire : pas de contrat OpenAPI / AsyncAPI à jour, pas d'Arazzo.

04 · Lire un fichier

Anatomie (1/2) : le fichier

Bloc Question Exemple
sourceDescriptions Avec quels contrats d’API ? quote-api.openapi.yaml
workflows Quel parcours ? souscrireHabitation
↳ dependsOn Quel parcours doit passer avant ? identifierClient
↳ inputs De quoi a-t-il besoin ? un JSON Schema
↳ steps Quelles étapes, dans quel ordre ? creerDevis → …
↳ outputs Que produit le parcours ? policyId
components Qu’est-ce qui se réutilise ? paramètres, reprises

⏱ 17:00 — Lire de haut en bas : avec quels contrats, quel parcours, ce qui doit passer avant, ce dont il a besoin, ce qu'il produit.

04 · Lire un fichier

Anatomie (2/2) : une étape

Champ Question Exemple
operationId Quel appel ? createQuote
parameters Avec quelles données ? $steps…outputs.quoteId
dependsOn Qui doit passer avant ? verifierEligibilite
successCriteria Réussi quand ? $statusCode == 201
onFailure Et si ça échoue ? retry, goto, end
outputs Que transmet l’étape ? quoteId

⏱ 18:30 — Aussi : requestBody (le corps de la requête) et onSuccess (goto / end en cas de succès). dependsOn existe à deux niveaux : entre workflows (composer des parcours) et entre étapes (prérequis explicite).

04 · Lire un fichier

Les expressions : le fil entre les étapes

Expression Lit…
$inputs.address une entrée du workflow
$statusCode == 201 le code HTTP de la réponse
$response.body#/id un champ de la réponse (JSON Pointer)
$steps.creerDevis.outputs.quoteId une sortie d’une étape précédente
$workflows.identifierClient.outputs.customerId une sortie d’un autre workflow
$sourceDescriptions.quoteApi.createQuote une opération d’un contrat d’API

⏱ 20:00 — Les expressions rendent la spécification précise : on sait exactement d'où vient chaque valeur. À retenir : $steps…outputs rend explicite ce qu'on se transmet entre équipes.

05 · Un exemple complet

Du devis à la police, en un workflow

Nominal : le parcours démarre après identifierClient (dependsOn de workflow), puis chaque étape lit les outputs de la précédente.

503 → retry : payer répond 503, onFailure relance jusqu'à 3 fois, toutes les 2 s. La reprise est écrite dans le contrat.

Ordre non respecté : payer appelé avant verifierEligibilite, or le contrat spécifie que payer en dépend.

⏱ 22:30 — Deux clics : nominal → retry → ordre non respecté.

Ordre non respecté : on ne paie jamais avant l'éligibilité. Le dependsOn rend cette règle contractuelle : le parcours la spécifie noir sur blanc.

05 · Un exemple complet

Le fichier (1/3) : sources et workflows

arazzo: 1.1.0
info: { title: Souscription habitation, version: 1.0.0 }
sourceDescriptions:                         # les contrats d'API, référencés
  - { name: quoteApi,   type: openapi, url: ./quote-api.openapi.yaml }
  - { name: paymentApi, type: openapi, url: ./payment-api.openapi.yaml }
  - { name: policyApi,  type: openapi, url: ./policy-api.openapi.yaml }
workflows:
  - workflowId: identifierClient            # étapes non détaillées ici
  - workflowId: souscrireHabitation
    dependsOn: [ identifierClient ]         # un parcours prérequis
    steps:                                  # diapos suivantes

⏱ 25:00 — dependsOn de workflow : souscrireHabitation ne démarre qu'une fois identifierClient terminé. On compose des parcours comme des briques.

05 · Un exemple complet

Le fichier (2/3) : les premières étapes

    steps:
      - stepId: creerDevis
        operationId: $sourceDescriptions.quoteApi.createQuote
        requestBody:
          payload: { customerId: $workflows.identifierClient.outputs.customerId }
        successCriteria: [ { condition: $statusCode == 201 } ]
        outputs: { quoteId: $response.body#/id }
      - stepId: verifierEligibilite
        operationId: $sourceDescriptions.quoteApi.checkEligibility
        parameters:
          - { name: id, in: path, value: $steps.creerDevis.outputs.quoteId }
        successCriteria: [ { condition: $response.body#/eligible == true } ]

⏱ 26:30 — Montrer : operationId pointe vers le contrat OpenAPI ; $workflows… réutilise la sortie du parcours prérequis ; $steps.creerDevis.outputs.quoteId fait circuler la donnée.

05 · Un exemple complet

Le fichier (3/3) : dependsOn d’étape

      - stepId: payer
        operationId: $sourceDescriptions.paymentApi.pay
        # Prérequis explicite. Selon la spec Arazzo, en synchrone l'ordre
        # de steps suffit : dependsOn sert surtout à l'asynchrone (annexe).
        dependsOn: [ verifierEligibilite ]    # jamais payer avant
        requestBody: { payload: { quoteId: $steps.creerDevis.outputs.quoteId } }
        successCriteria: [ { condition: $statusCode == 201 } ]
        onFailure:
          - { name: indispo, type: retry, retryAfter: 2, retryLimit: 3,
              criteria: [ { condition: $statusCode == 503 } ] }
        outputs: { paymentId: $response.body#/id }
      - stepId: emettrePolice
        operationId: $sourceDescriptions.policyApi.issuePolicy
        outputs: { policyId: $response.body#/policyId }

⏱ 28:00 — dependsOn d'étape : « liste des étapes qui DOIVENT être terminées avant celle-ci ». Il n'exécute rien : il pose un prérequis.

Être honnête : la spec recommande l'ordre du tableau pour le synchrone ; dependsOn est surtout pensé pour l'asynchrone (annexe). Son intérêt ici : rendre la règle métier explicite dans le contrat.

06 · Esprit critique

Pourquoi y aller, et ce qui peut coincer

Ce qu'on gagne

  • Une source de vérité du parcours, revue en PR
  • Spécifié : ordre, données, critères de succès
  • Norme ouverte : pas de verrou éditeur
  • Partagé : archis, devs et QA lisent le même fichier
  • REST + Kafka dans un même parcours (1.1)

Ce qui peut coincer

  • Norme jeune : peu de retours d'expérience
  • Prérequis : sans contrats d'API à jour, l'Arazzo ment
  • Maintenance : qui est propriétaire du fichier ?
  • Hors norme : les jeux de données

⏱ 30:00 — Être honnête sur les limites : c'est ce qui rend crédible.

06 · Esprit critique

Mon parti pris

Ne pas tout « arazzo-iser ». Un parcours critique, multi-équipes, qui casse en recette.

Si en 3 mois il n'a pas clarifié le parcours entre les équipes, on arrête.

⏱ 31:00 — Critère de succès explicite pour l'expérimentation : un parcours mieux compris entre équipes en 3 mois.

Annexe · nouveau en Arazzo 1.1

L’étape événementielle

- stepId: attendrePoliceEmise
  operationId: $sourceDescriptions.policyEvents.onPolicyIssued
  action: receive                       # send publie, receive attend
  dependsOn: [ payer ]                  # ici, dependsOn prend tout son sens
  correlationId: $steps.payer.outputs.paymentId
  timeout: 30000                        # ms
  successCriteria:
    - context: $message.payload
      condition: $.status == 'ISSUED'
      type: jsonpath
  outputs:
    policyId: $message.payload.policyId

Source type: asyncapi · correlationId aligné avec celui du contrat AsyncAPI · $message.payload lit le message reçu.

Annexe, à montrer si la question Kafka vient. C'est le cas d'usage principal de dependsOn d'étape selon la spec : coordonner l'asynchrone.
